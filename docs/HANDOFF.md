# Передача работы: где мы остановились

Записка для новой сессии Claude Code на сервере бота: что за проект, как здесь принято работать и что сейчас
разбираем. Подробности — в README.md, docs/GUIDE.md и сообщениях коммитов (`git log`).

## Проект

Telegram-бот на aiogram и мини-приложение («Медиатека») для Яндекс Музыки. Каждый пользователь подключает свой
аккаунт Яндекса. Бот работает на сервере владельца в Docker (`docker compose`), папка — `~/yamusicbot`.

Что умеет бот:
- поиск, скачивание, лайки, плейлисты, инлайн-режим;
- загрузка своих аудиофайлов в Яндекс с редактором тегов и обложки;
- статистика прослушиваний и точный подсчёт через Ynison;
- объединение и копирование плейлистов (`/merge`);
- общие плейлисты, которые бот синхронизирует между участниками (`/shared`);
- админ-панель, резервное копирование (`scripts/backup.sh`, `scripts/restore.sh`).

## Как здесь принято

- Пользователь пишет по-русски, отвечать по-русски, просто и по шагам.
- Ветка — `claude/telegram-yandex-music-bot-awmvt2`, она же основная. PR не создавать, пока не попросят.
- Коммиты с тегами соавторства (см. `git log -1`), без названий моделей в тексте.
- Перед пушем: `ruff check .` и `python -m pytest -q`, всё должно быть зелёным.
- Токены и пароли никогда не просить прислать в чат; бот сам их в чат не пишет.
- Бережно к лимитам Яндекса: все запросы идут через общий регулятор `bot/net.py` (Guard), фон — через
  `net.background()`. Однажды Яндекс уже ограничивал IP сервера за частые запросы, тогда помогла смена IP.
- Обновить бота на сервере: `cd ~/yamusicbot && git pull && docker compose up -d --build --force-recreate`.
- Логи: `docker compose logs --since 1h bot`.

## Открытые вопросы (на 26.10.2026)

1. **Обложка из редактора не ставится в Яндексе.** Пользователь меняет обложку в «Медиатеке», трек загружается,
   но в Яндекс Музыке видна исходная обложка. Со стороны бота проверено: мини-приложение отправляет картинку,
   `prepare_for_upload` записывает её в MP3 (APIC, ID3v2.3), а с ec1cae6 любая обложка перекодируется в JPEG до
   1200 точек. Главная гипотеза: тот же трек до этого уже загружали несколько раз, и Яндекс по содержимому аудио
   узнаёт прежнюю загрузку и берёт её данные. Проверить на сервере: загрузить трек, который ещё ни разу не
   загружали, с новой обложкой. Посмотреть логи (`grep -iE "загруж|обложк|ugc"`). При необходимости сохранить
   подготовленный файл и проверить его обложку через mutagen или ffprobe.
2. **Трек иногда не появляется с первой загрузки.** Сделано:
   - 25f2d10: перед первой загрузкой сессия получает cookies;
   - bot/placer.py: если трек не появился за 4–10 минут, файл отправляется ещё раз;
   - 5c8fcc3: повтор при 5xx и таймаутах.

   Пользователь видел ответ сервера загрузки Яндекса «HTTP 504 upstream request timeout». Нужны логи загрузки,
   чтобы понять, что именно происходит: адрес загрузки, номер ugc, повтор.
3. **Точный подсчёт (Ynison) не работает с 9–10.10.2026.** `python -m bot.diag_ynison` показывает «Ynison
   service is temporary unavailable» (gRPC 14, go-away 3600) и для устройства бота, и для нового устройства.
   Вероятно, это сбой у Яндекса после атак на дата-центры 8–9.10. Бот сам ждёт и переподключается.
   Если сайт music.yandex.ru видит, что играет на телефоне, а с сервера Ynison всё ещё недоступен, — дело в IP
   сервера (можно попробовать YANDEX_PROXY).
4. **Перенос медиатеки Spotify ⇄ Яндекс.** Начат и поставлен пользователем на паузу; заготовка лежит в
   `git stash` облачной сессии (на сервере её нет). Не возобновлять без просьбы.
